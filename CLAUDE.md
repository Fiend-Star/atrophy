# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Atrophy is a local-first CLI (npm package `atrophy`) that measures a developer's unaided coding skill over time: short drills graded automatically, an Elo-style rating per skill axis, and a dashboard showing decay curves and the unaided-vs-AI-assisted gap. `PLAN.md` is the founding design doc and is still referenced from code comments (e.g. "PLAN §3.4").

## Commands

```sh
npm test                              # vitest run (all tests; spawns real python/node grading subprocesses)
npx vitest run engine/scoring.test.ts # one test file
npx vitest                            # watch mode
npm run typecheck                     # tsc --noEmit
npm run build                         # tsc -p tsconfig.build.json → dist/
npm run dev -- drill --show           # run the CLI from source (tsx); everything after -- is CLI args
npx tsx cli/index.ts drill --lang java # same thing, but flags survive: npm (at least on Windows) eats the `--…` args after `--`, so `npm run dev -- drill --show --lang java` reaches the CLI as `drill` alone
npm run seed:demo                     # regenerate dashboard/demo-data.json
```

Requires Node ≥ 22 and Python 3 on `PATH` (Python exercises and their integrity tests actually run `python`). Java work additionally needs a JDK ≥ 21 (`javac`/`java`): every Java suite is wrapped in `describe.skipIf(!hasJdk())` and prints a "SKIPPED" warning, so **a green `npm test` without a JDK has not tested Java at all**. Shell work needs bash ≥ 4 the same way (`describe.skipIf(!hasBash())` on `bank-integrity.test.ts`'s shell arms, same "not validated" warning) — macOS's stock bash 3.2 is one of the hosts this hides rather than nags. Neither CI leg needs a setup step for it: ubuntu-latest has bash natively and windows-latest ships Git for Windows (Git Bash) already, which is also where `atrophy` itself finds bash on Windows (see `engine/bashtool.ts` below) — a bare `bash` on a Windows PATH is the WSL launcher, not Git Bash, so discovery never falls back to that name. CI (`.github/workflows/ci.yml`) runs typecheck + test + build on ubuntu **and windows**, Node 22 and 24, with Python 3.12 and Temurin JDK 21 installed on every leg — keep code Windows-safe (see the `SystemRoot`/`where` handling in `engine/runner.ts` and `engine/session.ts`, and filename-safe timestamps in `cli/index.ts`).

Useful env vars when developing: `ATROPHY_DB` (SQLite path override — point at a throwaway file, the default is the user's real `~/.atrophy/atrophy.db`), `ATROPHY_NO_SYNC=1` (kill-switch for all leaderboard network calls; set it whenever recording ai-off sessions in dev/tests so junk never reaches the public board), `ATROPHY_BANK` (**replaces** the built-in bank dir), `ATROPHY_PACKS` (**additive** pack dirs, `path.delimiter`-separated — `;` on Windows), `ATROPHY_JAVA_HOME` (JDK override; `javac`/`java` are resolved as `$ATROPHY_JAVA_HOME/bin/…`, which is how you get past a `.cmd` shim from scoop/mise — the runner spawns without a shell and cannot execute one), `ATROPHY_BASH` (bash override, taken verbatim rather than as a `bin/`-relative root — the `ATROPHY_PYTHON` shape, not the `ATROPHY_JAVA_HOME` one — the escape hatch for MSYS2, Cygwin, or a deliberate WSL choice), `ATROPHY_PYTHON`, `ATROPHY_EDITOR`, `ATROPHY_CONFIG`, `ATROPHY_LEADERBOARD_URL`.

Validating an exercise pack — the content gate CI runs, pointed at the pack instead: `$env:ATROPHY_BANK="<pack-dir>"; npx vitest run bank/bank-integrity.test.ts`. `ATROPHY_BANK` **replaces** the bank, so this checks the pack alone and can only catch id collisions *within* it; a collision with a shipped exercise shows up in `atrophy doctor`, which loads base + packs merged.

Interactive drills block on stdin/$EDITOR. For non-interactive runs use `--show` (preview, nothing recorded) or `--solution <file>` (grades a pre-written answer file; how the e2e-ish tests drive drills). `atrophy setup` (persist a language allowlist and a track focus to config) blocks on stdin too — numbered picks, blank/`0` meaning "all"; its flag form (`--languages <csv>` / `--all-languages` / `--track <name>`) is the scriptable path and validates everything before writing anything, so a bad entry writes no config at all; `setup --show` prints current state plus the discovered-track table and never writes (it loudly ignores the write flags).

## Architecture

ESM throughout (`"type": "module"`, NodeNext): **relative imports use `.js` extensions even inside `.ts` files**. Strict TS with `noUncheckedIndexedAccess`. Tests are colocated `*.test.ts` next to their source, and `vitest.config.ts` exists only to exclude `**/.claude/**` so the suite never crawls an agent worktree's duplicated copies. One of the test files tests the docs: `cli/readme-claims.test.ts` recomputes, from the built-in bank and the generator registry, the facts README's five-skills table and `--lang` row assert (per-axis offerable kinds, which axes carry `language: "sql"` content, the axes each concrete `--lang` reaches under a full toolchain — `shell`'s expected set is only the `"any"`-tagged axes, since the built-in bank ships zero shell-tagged content, which is the row's "language-agnostic drills still qualify" claim in its purest form — java static/family counts and per-axis coverage) — so bank content and that README section have to move in the same commit.

Data flows in one direction: `bank` (content) → `engine` (logic) → `store` (SQLite) → `cli` (orchestration + HTTP payload) → `dashboard` (rendering).

- **`bank/`** — exercise content. `schema.ts` is the single source of truth: a zod discriminated union on `kind` — `write`/`fix` (code vs hidden tests), `write-harness`/`fix-harness` (Java-only behavioral drills: the exercise ships its own `testCode` harness plus a declared `totalChecks`, enforced at grade time), `predict-output` (type the snippet's stdout), `cloze` (fill the blanks — a snippet holds one or more `____`, and **every blank is a graded unit**: `acceptedAnswers` as `string[][]` is one set per blank, so the session asks per blank and partial credit is real, while a flat `string[]` is one answer that fills every blank and grades all-or-nothing), `outline` (self-scored rubric), `recall` (short answer, numeric-tolerant — `1/4` == `0.25` == `25%`; optional `reveal` is shown after grading, never graded; its `language` is a concrete `Language` **or** `"any"`, the same shape generator families use — a drill about `-XX:` flags or SQL window functions starts no toolchain but is not language-agnostic either, and `"any"` stays the tag for the ones that genuinely are; `outline` is the only arm still pinned to `"any"`). **among the graded-code kinds sql is `write`-only** (`fix` and `predict-output` reject `language: "sql"` by name; a `cloze` or a `recall` may carry it as a tag — those grade by matching what the user typed, so nothing runs): it drops `functionName`/`tests` for `cases` — each a `fixture` of DDL+INSERTs and the `expectedRows` one `SELECT` must return — with ≥ 2 cases *expecting different rows* enforced at parse time, since a single hardcoded literal would otherwise answer the drill; optional `ordered: true` makes row order part of the answer. shell is the fifth language and, like sql, `write`-only among the graded-code kinds (`fix`/`predict-output` reject `language: "shell"` by name; a shell `cloze`/`recall` is fine — string-matched, nothing runs): it drops `functionName`/`tests`/`cases` for `shellCases` — each case an optional `files` map of relative paths staged into a fresh per-case directory (`stagedFileKeyProblem` rejects a key using `\`, a rooted or drive-letter path, an empty/`.`/`..` segment, or the name `solution.sh` itself, case-insensitively), optional `args`, `expectedStdout`, and `expectedExitCode` (0–255, default 0) — with ≥ 2 cases differing in the *(stdout, exitCode)* pair enforced at parse time, sql's distinct-rows rule for a language where an echoed literal is the obvious cheat. A shell write ships its answer as a `<id>.reference.sh` sidecar beside the exercise JSON rather than a JSON field (`loadBank` only walks `*.json`, so it can never be picked up as an exercise, and `package.json` `files` can exclude the sidecar where a JSON key never could); `bank-integrity.test.ts`'s shell arms (`describe.skipIf(!hasBash())`, warning like the Java suite when bash is absent) grade every reference for a real 1.00, re-grade it to prove the same script scores identically twice, and run an echo of case 1's own expectation to prove that cheese cannot pass every case — plus an always-on, no-bash-needed `shellScriptProblems` lint over every shipped script (fixtures and reference alike): one pass over stripped text for banned constructs (`$RANDOM`, `~`, unpinned `PATH=`, `date +%Z`, `grep -P`), and a syntax-only pass flagging anything invoked that is neither a bash builtin nor in `PINNED_TOOLS` (catches `jq`/`curl`/`rev` as well as backgrounding via `&`/`nohup`/`disown`), plus a few host-variance traps (`date` with no fixed input, `du`, `ls -l`, a bare `env`, or a `find`/associative-array walk with no `sort`). The built-in bank ships no shell exercises yet — `bank-integrity.test.ts` asserts that list empty until it does, to be flipped in the same commit as the first one — so today's shell content lives entirely in packs. Code-like kinds may set `submitPolicy: "single"` (whiteboard mode: one graded submission, no fix-and-resubmit loop; absent means "loop"). Static exercises are one JSON file each under `bank/exercises/<axis>/`. `loadBank` takes one dir or several (built-in bank + packs) and rejects a duplicate id across them; it is a thin projection of `loadBankDetailed`, which also keeps which root dir's walk found each exercise — the provenance track focus filters on. The walk skips `pack.json`: that file is pack *identity*, not an exercise — `cli/tracks.ts` reads its `name` (lowercase `[a-z0-9-]{1,32}`; `all` and `base` are reserved) as the pack's track name, falling back to the dir basename lowercased, never throwing. `bank/generators/` holds generator *families* that render endless variants; the determinism contract is `generate(seed, tier)` must return an identical exercise for identical inputs, because the seed is embedded in the exercise id (`family-<6 hex>`) and replay rebuilds from it. `generators.test.ts` pins every family's declared shape and a hash of one render, so editing a family's output is a deliberate act (it stops every recorded session from replaying to what the user saw); a family's `language` may be a concrete `Language` or `"any"` for language-agnostic drills. `bank-integrity.test.ts` is the CI gate for content: every `fix` exercise's planted bug must actually fail a test, every `predict-output` snippet must run cleanly and deterministically, every cloze must contain `____` (and a per-blank `acceptedAnswers` must have exactly one set per blank), and every sql fixture must build the same database twice while the synthesized `UNION ALL`-of-literals cheese — rebuilt from the first case that expects rows — fails at least one case.

- **`engine/`** — all logic, no persistence. `scoring.ts`: Elo per axis (tiers act as fixed-rating opponents) plus Glicko-style RD — the core product invariant is **inactivity widens RD (confidence) but never lowers the rating; the rating only moves with drill evidence**. `select.ts`: picks the tier where predicted success is closest to 65%, mixes generator families (weighted 2×) with statics, avoids recently seen families, soft-caps a recently dominant language (`recentLanguages`, spec E1: a concrete language holding ≥ 3 of the last 6 recorded sessions has its candidates' weight multiplied by 0.25 — soft because the weights renormalize inside the pick and the pool is never filtered, so an all-one-language pool still serves; `"any"` rows occupy window slots but never count toward dominance and never pay the penalty; an explicit `language` disables the cap outright, because `--lang` is the user steering and selection never fights it), filters by the config language allowlist (`allowedLanguages`, under the same steering rule: it applies only when no explicit `language` was given, `"any"` content always passes, and an empty or absent list means no filtering; `hiddenByLanguages()` mirrors `hiddenByToolchain()`'s two-arm shape with both arms on the real toolchains, so a JDK-hidden java drill is never counted by both), and offers nothing it cannot grade — with no JDK, java exercises and families whose grading starts a JVM (`spawnsJvm`: the `JVM_KINDS` plus `predict-output`) drop out of `selectExercise` and `availableAxes`, and with no bash a shell `write` (`spawnsShell`, shell's one graded-code kind) drops out the same way, while a java or shell `cloze` stays (string-matched in-process). `Toolchains` is `{ jdk, bash }`, and one `TOOLCHAIN_GATES` table drives both `gradable()`/`blockedBy()` (a candidate's missing gate is attributed to exactly the first toolchain it trips, so nothing is ever double-counted) and `hiddenByToolchain()`'s per-toolchain breakdown (`HiddenByToolchain = { jdk, bash }`), which is what the CLI reports so a shrunken pool is never silent, and never blamed on the wrong toolchain. Inject `toolchains: { jdk, bash }` to test either without probing the host. `session.ts`: the interactive drill loop per exercise kind — writes a solution file in a temp dir, opens `$EDITOR`, submit/resubmit/abandon via readline. `grader.ts`: emits Python/Node harness scripts that print `ATROPHY_RESULT <json>`; comparison is canonical-JSON equality — for Python specifically, that comparison runs both sides through a `normalize()` step mirroring the same number model Java's codec uses (a finite integral `float` with `|v| <= 2^53` renders as its `int` form; `NaN`/±`Infinity` render as `null`; `bool` is left untouched, since `isinstance(v, float)` is `False` for Python's `bool`), so an int-returning and a float-returning solution grade identically on an integral value, matching JS/Java parity - this is a **grading-semantics contract**, not an implementation detail (JS has no int/float distinction to begin with, so `nodeHarness` needs no equivalent). Java instead compiles and runs a *shipped* harness: `javac` then `java` (two steps, so a compile error is reported as one, and compilation gets its own 30 s budget separate from the drill's `testTimeoutMs`), with `engine/java/Harness.java` (reflection over `Solution`, its own JSON codec mirroring `JSON.stringify` number semantics) for `write`/`fix`, and `engine/java/Atrophy.java` (`plan`/`check`/`report`/`watchdog`) beside the exercise's own `testCode` for the harness kinds. `predict-output` in Java skips `javac` entirely — single-file source launcher (`java Main.java`). sql needs no toolchain to find: `gradeSql` stages a generated `.cjs` harness that `require`s the CLI's *own* better-sqlite3 by resolved absolute path (the temp dir has no `node_modules`), then runs the submitted `solution.sql` against a fresh `:memory:` database per case — `query_only = 1` is set after the fixture applies, so a DELETE-then-SELECT "answer" is a named failure rather than a pass, and comparison is `canonicalRows` (keys sorted, rows sorted unless `ordered`). shell needs bash resolvable at all (`bashCommand()`, else a `bashUnavailable` harnessError) and grades by actually running the script: `gradeShell` CR-strips only the submitted script (fixture `files` stage byte-exact — a fixture may legitimately need CRs the drill's *answer* must not), then per case builds a fresh sub-directory (`files` written by Node, never a shell prelude, with the script copied over the top), runs it under the case's full `testTimeoutMs` with `HOME` pinned to that case's own forward-slashed directory, and compares `normalizeOutput(stdout)` plus exit code with no partial credit for a near-miss (unlike `predict-output`'s whitespace-only credit). A `command not found` naming a `PINNED_TOOLS` member is classified as a `harnessError` rather than scored, but only once a case has already failed on its own merits (checking it on a passing case would void a correct answer over stderr the drill never graded); a timed-out case voids the whole attempt, same as a bank-bug in sql. `cloze` and `recall` spawn nothing at all: both grade in-process — cloze by a normalized (trim + collapse inner whitespace, still case-sensitive) match per blank, recall through the numeric tolerance above. `javatool.ts` owns JDK discovery (`ATROPHY_JAVA_HOME`, cached `hasJdk()` probe, `MIN_JDK_MAJOR = 21`, `parseJavaMajor`), the resource path lookup, and `JAVA_RUNTIME_FLAGS` — **six** pinned flags on every graded JVM: `-Dfile.encoding`, `-Duser.language`, `-Duser.country`, `-Duser.timezone`, `-Dstdout.encoding`, `-Dstderr.encoding` (the last two are not redundant: since JDK 19 `file.encoding` no longer covers a redirected `System.out`, which is exactly what grading reads). `bashtool.ts` is the same shape for shell — `ATROPHY_BASH` taken verbatim, a cached `hasBash()` probe, `MIN_BASH_MAJOR = 4`, `parseBashMajor` — but with a hazard java's discovery does not have: on win32 the bare name `bash` on `PATH` is the WSL launcher, so discovery there never falls back to a bare name, only to a path it derived (`git --exec-path`, three parents up to `usr/bin/bash.exe`) or found at one of two well-known Git-for-Windows install locations, giving up otherwise. `SHELL_ENV()` is the `JAVA_RUNTIME_FLAGS` analog as environment: `LC_ALL`/`LANG` pinned to `C`, `TZ` to `UTC`, MSYS path-conversion disabled (`MSYS_NO_PATHCONV`, `MSYS2_ARG_CONV_EXCL`), and `PATH` rewritten so bash's own dir wins first — unpinned, a script launched from a non-shell parent loses most of `PINNED_TOOLS` (the frozen Git-Bash-`usr/bin` inventory a shell drill may assume, deliberately missing `jq`/`python`/`curl`/`rev`) to a silent `command not found`-with-exit-0, or worse has `sort`/`find` silently resolve to different System32 programs. `runner.ts`: the sandbox — subprocess with no shell, minimal env, hard timeout, capped output. `rng.ts` (mulberry32), `guard.ts` (detect running AI assistants — warn, never block), `regression.ts`/`streak.ts`/`timeline.ts` (analytics precomputed for the dashboard).

- **`store/db.ts`** — better-sqlite3, two tables (`sessions`, `ratings`), idempotent `CREATE IF NOT EXISTS` migration. `getRating()` applies RD time-decay on read.

- **`cli/`** — commander entry point `cli/index.ts`; `drillOnce()` is the orchestrator tying select → guard → session → scoring → store → auto-sync; it feeds the mix soft-cap by passing `store.recentSessionLanguages(6)` only when no `--lang` was given *and* the caller left `opts.languageMix` alone — `baseline` passes `{ languageMix: false }`, so its forced per-axis sweep never skews its own later picks. `bankRoots()` resolves the built-in bank (or `ATROPHY_BANK`) plus `config.ts`'s `packDirs()` — `ATROPHY_PACKS` then `"packs"` from `~/.atrophy/config.json`, canonicalised and de-duplicated; a missing pack dir throws with the pack named — and keeps base and packs *apart*, because a track names exactly one of those roots (`bankDirs()` is the flattened list `loadBank` wants). The same config file carries the two preferences `atrophy setup` (`cli/setup.ts`) writes: a `languages` allowlist (`configLanguages()` drops unknown entries rather than failing — doctor is where a typo gets named) and a `track` focus (`configTrack()` treats blank and `"all"` as no focus: `"all"` is the reserved escape hatch `--track all`/`setup --track all` write, and doctor/setup print it back as the normal state, so a hand-edited config using the word the output teaches must read back fine). `drill`/`baseline` resolve their pool through both before selecting: track focus (`--track` beats config) filters statics to that track's root and — unless the track *is* base — serves **no** generator families, since the built-in families are base content; the allowlist rides into selection except under `--lang`; `--exercise` replay bypasses both, an explicit id not being a request for a pool. `setupAction` and doctor's `checkConfig` take the bank roots injected instead of importing `bankRoots` back from `cli/index.ts` — that import would be a cycle. `doctor.ts` is the environment self-diagnosis (`checkJava` warns rather than fails — Python/JS drills are unaffected by a missing JDK; `checkBash` is the same warn-only shape for shell drills, but also names which discovery rule resolved bash (`git --exec-path`, a well-known install, or PATH) since on Windows the real question is whether it found Git Bash or WSL; `checkSql` reports the bundled SQLite's version rather than searching for a toolchain, and warns rather than fails because there is nothing a user could go install; `checkConfig` warns-never-fails for the same reason — it prints the allowlist, the track focus, and the discovered-track table with per-track drill counts, flagging unknown config languages, a track matching nothing, and an *ambiguous* track name, i.e. one claimed by more than one pack: doctor and setup warn about those, but `findTrack` throws on use — the fix is a rename via `pack.json`). `serve.ts` `buildPayload()` is the **entire data contract** shared by `atrophy serve`, `atrophy export`, and the dashboard — change it and all three move together. `publish.ts` handles leaderboard opt-in and post-drill auto-sync (quiet on failure by design).

- **`dashboard/`** — a single self-contained HTML file, no build step, no CDN; it only draws what `buildPayload` precomputed. Deployed as a demo (with `demo-data.json`) to GitHub Pages by `.github/workflows/pages.yml`.

- **`leaderboard/`** — separate deployment: a Cloudflare Worker + D1 (`wrangler.toml`), not part of the npm package or CI.

## Invariants to preserve

- `--ai-on` sessions are recorded (for the divergence chart) but must **never touch the unaided rating** — that gap is the product's reason to exist.
- Generated exercise ids are `family-<6 hex seed>` and must reproduce exactly; in `resolveExercise` static bank ids win over generated-looking ids.
- Dual path resolution: the CLI runs from source (`cli/…` via tsx) and built (`dist/cli/…`), so asset lookups (`bankDir`, `dashboardHtmlPath`, `cliVersion`, `javaResourceCandidates`) try both `..` and `../..`. Anything new that loads a packaged asset needs the same treatment, and `package.json` `files` must include it (`engine/java` is there because the `.java` sources ship as-is — they are compiled on the user's machine, never by `tsc`).
- `engine/java/Harness.java` and `Atrophy.java` stay in the **unnamed package** — no `package` line, ever. Package-private invocation is the whole point: starter signatures are package-private, so `Harness` can only reach them (without `setAccessible`) by sharing the unnamed package with `Solution`.
- A harness reporting a different check count than the exercise declares is an exercise bug, never a score: `gradeHarness` replaces the result with a `harnessError` naming both numbers, and clamps `passed` into `[0, totalChecks]` before anything is rendered or stored. More generally, a `harnessError` is never evidence about the user — a missing JDK, a `javac` error, a broken exercise fixture, a timeout in *any* language (a killed run prints no marker, so `parseMarker` reports one), or the output cap (`RunResult.truncated` in `runner.ts`; `parseMarker` names it honestly - "output reached the 256KB cap … not necessarily an exercise bug" - rather than the generic unparseable-marker message; pre-existing behavior, just a better message now, but it sits slightly awkwardly beside "never evidence about the user," since a run that hits it can be partly attributable to the user's own solution printing or throwing something huge). So in the drill loop it does not consume a `submitPolicy: "single"` submission, does not print a score line (`0/n` would read as a verdict), and does not arm the `[s] stop here` option — which would otherwise let the user record a non-abandoned 0 and move the rating. The loop just re-prompts; the `--solution` path, having no loop, abandons instead.
- Track focus and the language allowlist are steering defaults, never locks: an explicit `--lang` bypasses the allowlist (and the mix soft-cap), `--track all` clears the focus for one run, and `--exercise` replays anything. And narrowing is never silent — the drill announces the active track and the axis's `hiddenByLanguages`/`hiddenByToolchain` counts (the latter now `{ jdk, bash }`, one bucket per toolchain); when a pool comes up empty the CLI names every *operative* cause together rather than one at random (the allowlist via `hiddenIfEquipped`, each toolchain gap via `toolchainGaps`) and never claims "no exercises in the bank" when the bank has them and only this host cannot grade them; `baseline` names each axis its config skipped outright, and separately names each axis a toolchain took off the sweep entirely (`toolchainSkipNotices`) — computed against the real toolchains on both sides, so a JDK/bash-hidden axis is never blamed on the config alone, but naming the config too (`ifEquipped`) when it would have skipped that axis even on a fully equipped host; and a `--lang` outside the allowlist warns on stderr (piped stdout stays drill content) but serves.
- AI-off enforcement is honor-system: detect and warn, never block. Similarly, network failures during leaderboard sync must never interrupt a drill.

## Contributing exercises

The most common contribution: one JSON file under `bank/exercises/<axis>/`, id matching the folder's prefix scheme (e.g. `dbg-py-005`; the java statics are `sr-java-`/`dbg-java-`/`cr-java-`/`api-java-`/`dec-java-`, and the java generator families are `sr-java-cond`/`dbg-java-scan`/`cr-java-trace`/`api-java-blank`), validated by `bank/schema.ts` and gated by the integrity tests above. Run `npm test` before pushing — a broken exercise cannot merge.

Numeric `tests` values need the same ±2^53 care regardless of target language, not just Java's (pre-existing behavior, shared by construction since the exercise JSON always goes through Node's own `JSON.parse`/`JSON.stringify` first - not something the engine-backlog fixes changed). No harness rejects an out-of-bound integer - none can, because the literal has already been rounded by Node's `JSON.parse` before any grading language sees it (Java parses what it is handed exactly as `long`, so it never fires a named error either; an integrity-time check would be the only place to enforce the rule); Python's `normalize()` (see the codec sentence above) declines to fold a `float` into its `int` form past that same bound, on purpose - matching Java - but the practical effect for a Python exercise authored right at the edge is a confusing verdict rather than a rejection: an `expected` and an `actual` that differ only past 2^53 can print as the same digits in a failure line. Relatedly: an exercise that means to grade the int-vs-float distinction itself needs at least one case whose correct value does **not** divide evenly - `normalize()` only folds an *integral* `float` together with its matching `int`; a genuinely fractional value like `180.5` still fails against `180` exactly as before.

Java authoring rules the harness enforces (each surfaces as a named grading error, not a crash — but the exercise is still wrong):

- `starterCode` keeps `public class Solution` with no `package` line. The graded method may be package-private (what the fixtures use — reflection reaches it via the shared unnamed package) or public, **never private**.
- The graded method must be unique by arity. Same name + same parameter count + different parameter types is rejected ("overloads are not supported"), inherited ones included; an *override* is fine — same signature twice collapses to the most-derived declaration, and synthetic bridge methods are skipped so a generic superclass does not read as a phantom overload.
- `Map` parameters must declare a literal `String` key type (`Map<String, Integer>`); JSON object keys are strings, so a wildcard, a type variable, or `Map<Integer, …>` is rejected.
- Integer values in `tests` stay within ±2^53 (see the general note above - an authoring rule, not something the harness enforces). Java parses what it is handed exactly as `long`, but the exercise JSON goes through Node's `JSON.parse` first, so anything larger is already a different number before grading sees it.
- Every Java `starterCode` must **compile**: the integrity suite runs `javac` over each one and expects exit 0. A `fix`/`fix-harness` bug therefore has to be semantic (wrong bound, missed lock, lost update), never a syntax or type error.
- Harness kinds: `testCode` is a complete `public class Harness` with `main` that prints exactly one `ATROPHY_RESULT` line (use `Atrophy.plan`/`check`/`report`, and `Atrophy.watchdog(ms)` well under `testTimeoutMs` so a deadlock still reports), and its total must equal `totalChecks`.
- A harness must **always report**, including on the buggy starter it ships with. Integrity grades every harness starter and requires a real result (no `harnessError`): an exception that escapes `main` prints no marker line, which grades as a harness error rather than as the failure the drill is supposed to teach. So wrap the checks:

  ```java
  try { /* checks */ } catch (Throwable t) { Atrophy.check("harness crashed: " + t, false); } finally { Atrophy.report(); }
  ```
